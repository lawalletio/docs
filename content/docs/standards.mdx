## NFC flows

### POS reads a Boltcard

The card holds a one-time `lnurlw://` URL. The POS turns it into a withdraw.

<Flow steps={[['Card', 'NDEF URL'], ['POS', 'GET lnurlw'], ['Card server', 'invoice'], ['POS', 'paid'], ['Done']]} />

1. POS reads the card's NDEF URI record. The URL has fresh `p` and `c` params on every tap (Boltcard SUN).
2. POS calls it and gets an LUD-03 `withdrawRequest`.
3. POS sends its own invoice to the `callback`. The card server checks `p`/`c` and pays it.

### Wallet reads a card or sticker

The phone wallet, in reader mode, reads the same NDEF URL and handles it: `lnurlw://` to withdraw (LUD-03), `lnurlp://` or `https://` to pay.

<Flow steps={[['Card / sticker', 'NDEF URL'], ['Wallet (reader mode)', 'LNURL'], ['Server']]} />

### Phone to phone: wallet pays a POS

While showing an invoice, the POS uses HCE to emulate a Type 4 tag holding `lightning:<bolt11>`. The wallet reads it like any tag and pays.

<Flow steps={[['Wallet (reader mode)', 'SELECT NDEF AID'], ['POS (HCE tag)', 'lightning:lnbc…'], ['Wallet', 'pay'], ['Done']]} />

The read is plain Type 4 Tag APDUs:

| Step | APDU | Meaning |
|------|------|---------|
| 1 | `SELECT D2760000850101` | NDEF application (v2) |
| 2 | `SELECT E103` + `READ BINARY` | Capability Container |
| 3 | `SELECT E104` + `READ BINARY` | NDEF file: 2-byte length + message |

No invoice on screen means the POS answers `6A82` (not found), so phones see no tag.

### Phone to phone: wallet app closed

A POS also polls for cards, so it may read the phone instead. The wallet registers an HCE service for the NDEF AIDs only to wake itself.

<Flow steps={[['POS', 'SELECT NDEF AID'], ['Wallet HCE', '6A82 + open app'], ['Wallet (reader mode)', 'reads invoice'], ['POS']]} />

| AID | Why |
|-----|-----|
| `D2760000850101` | NDEF v2, what readers SELECT first |
| `D2760000850100` | NDEF v1, Android's fallback after v2 fails |

The wallet answers `6A82` ("we're not a tag"), opens, and its reader mode reads the POS invoice on the next tap.
